## 들어가며
안녕하세요.  
예전에 [온프레미스 환경에서 GitOps를 구축한 이야기](/blog/6)를 썼었는데요,  
그 뒤로 한동안 잘 돌아가던 Argo CD를 다시 들여다볼 일이 생겼습니다.

계기는 단순했습니다.  
기존 웹 서비스 옆에 **새 웹 애플리케이션을 하나 더 띄워야 하는 상황**이었거든요.

그래서 "Application 하나 더 만들면 되겠지" 하고 구조를 열어봤는데...

> 어? 근데 Application 정의가 코드 어디에도 없네?

Argo CD 자체는 Terraform으로 설치하고 있었고,  
배포할 Helm chart들도 GitOps 저장소에 잘 들어가 있었습니다.  
그런데 정작 **"어떤 chart를 어느 namespace에 배포할지"** 를 정하는 Application은  
전부 Argo CD 대시보드에서 손으로 만든 것들이었습니다.

당장은 문제가 없지만, 이런 상태면 이런 일이 생깁니다.

- 클러스터를 다시 만들면 Argo CD는 설치되는데 **배포 대상이 하나도 없다**
- 누가 언제 sync 정책이나 values 경로를 바꿨는지 **기록이 안 남는다**
- 새 앱을 추가하려면 또 UI에서 클릭해야 한다

이번 글은 이 UI 기반 Application들을  
**서비스 중단 없이 App of Apps 구조로 옮긴 과정**을 정리한 글입니다.  
중간에 공용 Helm chart로 합치는 작업, 그리고 생각지도 못한 **NodePort 교착 상태**까지 만났네요. 😂

> Application 관리 주체를 옮기는 작업 자체는 무중단이었고,  
> 하는 김에 같이 진행한 포트 정리에서만 한 서비스가 잠깐(수십 초) 끊겼습니다. 이 얘기는 6장에서 하겠습니다.

## 1. 출발점: 구조 파악하기

먼저 현재 구조를 정리해보면 이렇습니다.

```
 소스 저장소 (web-a, web-b, license-server)
        │ Jenkins: 이미지 빌드 → Registry push
        │ Jenkins: GitOps 저장소의 values 파일에서 image.tag 수정 후 push
        ▼
 GitOps 저장소 (main)  ◄── Argo CD가 감시
        │
        ▼
 Argo CD → 각 chart를 k3s에 배포
```

GitOps 저장소 안에는 이런 chart들이 있었습니다.

```
gitops/
├── charts/
│   ├── web-a/
│   ├── web-a-develop/
│   └── license-server/
└── envs/
    └── prod/
        └── web-a-values.yaml
```

Jenkins는 빌드가 끝나면 `sed`로 values 파일의 `repository:`와 `tag:` 줄만 바꿔서 push합니다.  
여기까지는 전형적인 GitOps 흐름인데, **Application이라는 연결 고리만 코드 밖에 있었던 것**입니다.

## 2. App of Apps가 뭔데?

처음에 이 이름을 들었을 때 저도 잘 와닿지 않았습니다.

핵심은 이겁니다.

> Application은 "Git의 이 폴더를 → 클러스터의 이 namespace에 맞춰라"라는 설정이다.  
> 그런데 **Application 자체도 YAML**이다.

그러니 Application YAML들을 한 폴더에 모아두고,  
**그 폴더를 감시하는 Application을 하나 만들면** 됩니다.

```
[root Application]   ← 손으로(또는 Terraform으로) 만드는 건 이것 하나
   │ apps/ 폴더 감시
   ▼
 Application 3개 생성: web-a, web-a-develop, license-server
   │ 각자 charts/xxx 폴더 감시
   ▼
 실제 Pod, Service 등 생성
```

이렇게 하면 앱 추가는 `apps/`에 YAML 하나 push하는 것으로 끝나고,  
설정 변경은 전부 Git 커밋으로 남습니다.

| 작업 | UI에서 직접 | App of Apps |
|---|---|---|
| 새 서비스 추가 | UI에서 New App 클릭 | `apps/`에 YAML 1개 push |
| 설정 변경 이력 | 남지 않음 | Git 커밋으로 남음 |
| 클러스터 재구성 | 전부 다시 클릭 | root 1개만 만들면 자동 복구 |

## 3. root는 Terraform에, 자식은 Git에

자식 Application은 GitOps 저장소의 `apps/` 폴더에 둡니다.

```yaml
# apps/web-a.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: web-a              # UI에 있던 기존 앱과 이름이 같아야 한다 (중요)
  namespace: argocd
spec:
  project: default
  source:
    repoURL: http://gitlab.example.internal/infra/gitops.git
    targetRevision: main
    path: charts/web          # 4장에서 만드는 공용 chart (최종 형태 기준)
    helm:
      valueFiles:
        - ../../envs/prod/web-a-values.yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: service       # UI에 있던 기존 앱과 배포 대상 namespace가 같아야 한다 (중요)
  syncPolicy:
    automated:
      prune: false
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

몇 가지 포인트가 있습니다.

- `valueFiles` 경로는 **`path`(chart 폴더) 기준 상대 경로**입니다. 그래서 `../../envs/...`가 됩니다.
- `automated`가 있어야 Jenkins가 태그를 push했을 때 sync 버튼 없이 바로 배포됩니다.
- 전환 초기에는 `prune: false`로 두는 게 안전합니다. Git에서 뭔가를 실수로 지워도 클러스터에서는 지우지 않거든요.

root Application은 `apps/` 안에 두지 않았습니다.  
root가 자기 자신을 관리하게 되면 헷갈리기도 하고, 실수로 지웠을 때 전체가 날아갈 수 있어서요.

대신 이미 Argo CD를 설치하던 Terraform에 넣었습니다.  
제가 쓰는 `argo-cd` Helm chart(10.x)에는 `extraObjects`라는 값이 있어서, 설치할 때 임의의 리소스를 같이 만들 수 있습니다.  
chart 버전에 따라 값 이름이 다를 수 있으니, 쓰시는 버전의 `values.yaml`을 한 번 확인해보세요.

```hcl
resource "helm_release" "argocd" {
  name       = "argocd"
  repository = "https://argoproj.github.io/argo-helm"
  chart      = "argo-cd"
  namespace  = "argocd"

  values = [
    yamlencode({
      # ... 기존 설정 ...
      extraObjects = [
        {
          apiVersion = "argoproj.io/v1alpha1"
          kind       = "Application"
          metadata   = { name = "root", namespace = "argocd" }
          spec = {
            project = "default"
            source = {
              repoURL        = "http://gitlab.example.internal/infra/gitops.git"
              targetRevision = "main"
              path           = "apps"
            }
            destination = {
              server    = "https://kubernetes.default.svc"
              namespace = "argocd"
            }
            syncPolicy = {
              automated = { prune = false, selfHeal = true }
            }
          }
        }
      ]
    })
  ]
}
```

이러면 `terraform apply` 한 번으로 **Argo CD 설치 → root 생성 → 자식 Application 생성**까지 이어집니다.  
`terraform plan`에는 `helm_release` 1건 변경만 보이고, 자식 Application은 Terraform이 아니라 root가 만듭니다.

## 4. 겸사겸사, 공용 chart로 합치기

새 앱(web-b)을 추가하려고 chart를 보니, `web-a`와 `web-a-develop` chart가 **거의 똑같았습니다.**  
다른 건 리소스 이름, 그리고 develop에만 있는 HA 설정이나 추가 포트 정도였죠.

여기에 web-b, web-b-develop까지 복사하면 같은 템플릿이 4벌이 됩니다.  
환경변수 하나 추가하려면 4곳을 고쳐야 하고요.

그래서 **템플릿은 1벌, 앱별 차이는 values 파일로** 분리했습니다.

```
gitops/
├── apps/
│   ├── web-a.yaml            ─┐
│   ├── web-a-develop.yaml     │  모두 charts/web 하나를 쓰고
│   ├── web-b.yaml             │  valueFiles만 다르게 지정
│   └── web-b-develop.yaml    ─┘
├── charts/
│   └── web/                   ← 공용 chart
└── envs/
    ├── prod/web-a-values.yaml
    ├── prod/web-b-values.yaml
    ├── develop/web-a-values.yaml
    └── develop/web-b-values.yaml
```

템플릿에서 고정돼 있던 이름은 `{{ .Release.Name }}`으로 바꿨습니다.  
Argo CD는 별도 설정이 없으면 **Application 이름을 Helm release 이름으로 사용**하기 때문에,  
`apps/web-b.yaml`의 `metadata.name`이 곧 리소스 이름이 됩니다.

```yaml
# charts/web/templates/deployment.yaml (일부)
metadata:
  name: {{ .Release.Name }}
spec:
  selector:
    matchLabels:
      app: {{ .Release.Name }}
  template:
    spec:
      containers:
        - name: {{ .Release.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          env:
{{- with .Values.env }}
{{ toYaml . | indent 12 }}
{{- end }}
{{- if .Values.ha.enabled }}
            - name: HA_DISCOVERY_HOST
              value: "{{ .Release.Name }}-ha.{{ .Release.Namespace }}.svc.cluster.local"
{{- end }}
```

develop에만 있던 설정은 `ha.enabled`, `service.extraPorts` 같은 값으로 켜고 끄게 만들었습니다.

### 기존 이름은 반드시 유지하기

여기서 조심해야 할 게 있습니다.  
**기존 앱의 리소스 이름이 하나라도 바뀌면, Argo CD는 그걸 완전히 새 리소스로 봅니다.**  
새 이름으로 하나를 더 만들고, 예전 리소스는 `prune`이 켜져 있으면 삭제, 꺼져 있으면 그대로 남습니다.  
어느 쪽이든 원하던 결과는 아니죠.

특히 이런 것들은 치명적입니다.

- **Deployment의 `selector`** 는 변경이 불가능합니다(immutable). 라벨이 바뀌면 sync가 실패합니다.
- **PV 이름**이 바뀌면 PV/PVC가 새로 만들어집니다.

그래서 기존 앱은 values에서 예전 이름을 그대로 지정하고,  
새 앱만 `{{ .Release.Name }}` 기반 기본값을 쓰도록 했습니다.

```yaml
# templates/_helpers.tpl
{{- define "web.pvName" -}}
{{ .Values.persistence.pvName | default (printf "%s-license-pv" .Release.Name) }}
{{- end }}
```

```yaml
# envs/prod/web-a-values.yaml
persistence:
  pvName: web-license-pv       # 기존 이름 그대로
  pvcName: web-license-pvc
```

환경변수도 템플릿에서 values로 옮겼는데, **순서**까지 기존과 똑같이 맞췄습니다.  
env 목록 순서가 바뀌면 Pod 템플릿이 바뀐 것으로 취급돼서 롤링 재시작이 일어나거든요.

### 렌더링 차이 확인하기: helm template 비교

말로만 "같게 만들었다"고 하면 불안하니, 실제로 렌더링 결과를 비교했습니다.

```bash
norm() { python3 -c "
import sys,yaml,json
docs=[d for d in yaml.safe_load_all(sys.stdin) if d]
print(json.dumps(sorted(docs,key=lambda d:(d['kind'],d['metadata']['name'])),indent=1,sort_keys=True))"; }

# 기존 chart
helm template web-a charts/web-a -f old-prod-values.yaml | norm > before.json
# 새 공용 chart
helm template web-a charts/web -f envs/prod/web-a-values.yaml | norm > after.json

diff before.json after.json && echo SAME
```

YAML을 파싱해서 정렬한 뒤 비교하기 때문에,  
따옴표 스타일이나 리소스 출력 순서 같은 **의미 없는 차이는 무시하고 실제 내용만** 비교할 수 있습니다.

기존 앱 두 개 모두 `SAME`이 나온 걸 확인하고 나서야 전환을 진행했습니다.  
비교한 매니페스트에 차이가 없으니, 전환해도 Pod가 다시 뜨지는 않겠다는 확신이 꽤 생겼네요.

## 5. 핵심: Non-cascading 삭제로 리소스 넘겨받기

이제 가장 중요한 단계입니다.  
UI에서 만든 기존 Application을 root 관리로 옮겨야 합니다.

방법이 하나만 있는 건 아닙니다. 같은 이름이면 root가 기존 Application 객체를 그대로 덮어쓰게 둘 수도 있어요.  
다만 저는 UI에서 이것저것 바꿔둔 설정이 섞이는 게 싫어서,  
**기존 Application을 지우고 root가 새로 만들게 하는 방식**을 택했습니다.

Argo CD에서 Application을 지울 때는 방식이 두 가지 있습니다.

| 방식 | Application | 아래 리소스 | 서비스 |
|---|---|---|---|
| **Cascading** (기본값) | 삭제 | **같이 삭제** | 중단 |
| **Non-cascading** | 삭제 | **그대로 남음** | 계속 동작 |

Application에 `resources-finalizer.argocd.argoproj.io` finalizer가 붙어 있으면,  
삭제할 때 Argo CD가 이걸 보고 하위 리소스까지 정리합니다(Cascading).  
Non-cascading은 이 finalizer 없이 **Application 객체만** 지웁니다.

```bash
argocd app delete web-a --cascade=false
```

UI에서는 Delete 버튼을 누르면 삭제 방식을 고를 수 있습니다.

Non-cascading으로 지우면 Pod는 그대로 돌아가고, 관리 주체만 없는 상태가 됩니다.  
그 상태에서 root가 **같은 이름, 같은 배포 대상 namespace(`spec.destination.namespace`)** 로 Application을 만들면,  
Argo CD는 리소스에 남아 있는 추적 정보를 보고 "아, 내 거구나" 하고 이어받습니다.

이 추적 정보는 Argo CD 설정(`application.resourceTrackingMethod`)에 따라 다릅니다.

- 최근 버전 기본값: annotation `argocd.argoproj.io/tracking-id` (Application 이름 + 리소스 정보)
- 예전 기본값: label `app.kubernetes.io/instance: web-a`

어느 방식이든 **Application 이름**이 들어 있어서, 이름이 같아야 이어받을 수 있습니다.  
전환 중에 추적 방식 설정을 바꾸지 않는 것도 중요합니다.

```
1. 기존 UI 앱을 Non-cascading 삭제   → 리소스는 그대로 동작
2. terraform apply                    → root 생성
3. root가 apps/web-a.yaml 적용        → 같은 이름의 Application 생성
4. 새 Application이 기존 리소스 인수   → 서비스 중단 없음
```

그래서 전환 전에 **기존 앱의 namespace를 꼭 기록**해야 합니다.

```bash
kubectl get applications -n argocd \
  -o custom-columns=NAME:.metadata.name,NS:.spec.destination.namespace,PATH:.spec.source.path
```

namespace가 다르면 새 Application은 다른 namespace에 리소스를 **새로 만들어 버립니다.**  
그러면 남아 있던 기존 리소스와 NodePort, PV 이름이 겹쳐서 배포가 실패합니다.

## 6. 예상 못 한 함정: NodePort 교착 상태

전환 자체는 잘 됐는데, 몇몇 앱이 계속 `Sync failed` 상태였습니다.

```
Service "web-a" is invalid: spec.ports[0].nodePort:
Invalid value: 30083: provided port is already allocated
```

이번 기회에 포트도 정리하면서 두 앱의 포트를 **서로 맞바꿨던 게** 문제였습니다.

```
license-server : 30083 → 30081 로 가려면 web-a가 30081을 먼저 비워야 함
web-a          : 30081 → 30083 으로 가려면 license-server가 30083을 먼저 비워야 함
```

서로 상대가 먼저 비켜주길 기다리는 구조라,  
`selfHeal`로 아무리 재시도해도 **영원히 풀리지 않습니다.**  
다행히 기존 Service는 그대로 남아 있어서 서비스가 끊기지는 않았지만, 둘 다 OutOfSync로 멈춰 있었죠.

해결은 한쪽 Service를 잠깐 지워서 포트를 비워주는 것이었습니다.

```bash
# 1. license-server Service만 삭제 (Pod와 데이터는 그대로)
kubectl -n service delete svc license-server

# 2. web-a sync → 30083으로 이동하면서 30081을 비움
argocd app sync web-a

# 3. license-server sync → 사라진 Service를 30081로 다시 생성
argocd app sync license-server
```

license-server만 수십 초 정도 접속이 끊기고 끝났습니다.

혹시 1번과 2번 사이에 `selfHeal`이 license-server Service를 먼저 다시 만들려고 해도 괜찮습니다.  
license-server가 원하는 포트는 30081이고, 그 포트는 아직 web-a가 쓰고 있으니 생성이 실패하거든요.  
비워둔 30083을 license-server가 다시 가져갈 일은 없습니다.  
그래도 마음이 불안하다면 license-server의 자동 sync를 잠시 끄고 진행해도 됩니다.

참고로 한쪽만 비어 있는 포트로 옮기는 경우(예: A가 30084 → 30085로 가고, B가 비워진 30084를 쓰는 경우)는  
A가 먼저 옮기고 나면 B가 재시도해서 자연스럽게 해결됩니다.  
**순환(맞바꾸기)인 경우에만** 교착이 생깁니다.

포트 번호를 맞추는 게 꼭 필요한 게 아니라면, 처음부터 맞바꾸지 않는 게 제일 간단합니다.

---

## 마무리

정리하면 이번 전환의 흐름은 이랬습니다.

1. Application 정의를 `apps/`로 꺼내고, root는 Terraform `extraObjects`에 둔다
2. 공용 chart로 합치되, 기존 리소스 이름은 values로 그대로 유지한다
3. `helm template` 비교로 기존 렌더링과 같은지 증명한다
4. 기존 앱의 이름과 namespace를 기록하고 맞춘다
5. **Non-cascading**으로 기존 앱을 지우고 root가 이어받게 한다
6. 포트를 맞바꿨다면 한쪽 Service를 지워 교착을 풀어준다

돌아보면 기술적으로 어려운 건 없었는데,  
**"이름이 같아야 이어받는다"** 와 **"Cascading이 기본값이다"** 이 두 가지를 모르고 진행했다면  
꽤 큰 사고가 났을 것 같습니다. 😅

이제 새 앱을 추가할 때는 values 파일 하나와 Application YAML 하나만 push하면 끝입니다.  
UI에서 클릭하던 시절보다 훨씬 마음이 편하네요.

틀린 부분이나 더 좋은 방법이 있다면 댓글로 알려주세요!  
감사합니다. 😊
