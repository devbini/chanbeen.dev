## 들어가며
안녕하세요.  
최근 프로젝트 하나를 두 개의 저장소로 분리하면서,  
이미지 경로도 같이 바뀌었습니다.

```
registry.example.internal/team/legacy-app   (기존)
registry.example.internal/team/web-a        (신규)
registry.example.internal/team/web-b        (신규)
```

파이프라인 코드에서 이미지 경로만 바꾸면 끝날 줄 알았는데,  
그 뒤로 이틀 동안 이런 에러들을 차례로 만났습니다.

```
# 1. Jenkins (Kaniko push)
UNAUTHORIZED: authentication required

# 2. Kubernetes (Pod 이미지 pull)
pull access denied, repository does not exist or may require authorization:
server message: insufficient_scope: authorization failed
```

특히 두 번째는 **Secret을 바꿨는데도 그대로**여서 꽤 헤맸습니다.  
결론부터 말하면, 토큰을 직접 디코딩해서 **"이 토큰이 실제로 어떤 권한을 받는지"** 를 봤더니 바로 답이 나왔습니다.

이번 글은 이때 겪은 문제와 GitLab Registry 인증 흐름을 정리해봅니다.

---

## 1. 같은 Secret으로 예전 이미지는 되는데?

먼저 상황을 정리하면,

- Jenkins는 Kubernetes 위에서 돌고, 빌드할 때마다 Kaniko Pod를 띄웁니다.
- Kaniko는 `jenkins` namespace의 `regcred` Secret을 마운트해서 registry에 로그인합니다.
- **같은 `regcred`로 기존 경로(`legacy-app`)에는 push가 잘 됐습니다.**
- 새 경로(`web-a`)에는 `UNAUTHORIZED`가 났습니다.

로그인 정보는 같은데 경로에 따라 결과가 다르다는 건,  
**인증(누구인가)은 통과했지만 인가(무엇을 할 수 있나)에서 막혔다**는 뜻입니다.

확인해보니 `regcred`에는 **기존 프로젝트 전용 토큰**이 들어 있었습니다.  
그 프로젝트에만 권한이 있으니, 새 프로젝트에는 push할 수 없었던 거죠.

여기까지는 비교적 금방 찾았습니다.  
문제는 그다음이었습니다.

---

## 2. GitLab Registry 인증은 어떻게 동작할까?

두 번째 문제를 이해하려면, Registry 인증 흐름을 먼저 알아야 합니다.  
Docker Registry(v2)의 토큰 인증은 이렇게 동작합니다.

```
 클라이언트(kubelet, Kaniko 등)                Registry             GitLab
     │  1. GET /v2/team/web-a/manifests/...  │                     │
     │ ────────────────────────────────────► │                     │
     │  2. 401 + WWW-Authenticate:            │                     │
     │     Bearer realm=".../jwt/auth",       │                     │
     │     scope="repository:team/web-a:pull" │                     │
     │ ◄──────────────────────────────────── │                     │
     │  3. GET realm?scope=... (Basic 인증: 사용자/토큰)             │
     │ ───────────────────────────────────────────────────────────► │
     │  4. JWT 토큰 발급 (access 항목에 "허용된 권한"만 담김)         │
     │ ◄─────────────────────────────────────────────────────────── │
     │  5. 다시 요청 (Bearer JWT)              │                     │
     │ ────────────────────────────────────► │                     │
     │  6. 권한이 없으면 insufficient_scope   │                     │
```

여기서 중요한 포인트가 하나 있습니다.

> 4번 단계에서 GitLab은 요청한 권한을 **다 주지 않더라도 토큰 자체는 발급**해준다.  
> 다만 그 토큰의 `access` 항목에 **허용된 권한만** 담길 뿐이다.

그래서 권한이 없는 경우, 토큰 발급 단계에서 바로 막히는 게 아니라  
그 토큰으로 이미지를 요청한 6번 단계에서 `insufficient_scope`가 납니다.  
"요청에 필요한 권한이 이 토큰에 없다"는 뜻이죠.

참고로 `insufficient_scope`는 HTTP 상태 코드가 아니라 **오류 사유**라서,  
응답 자체는 401과 함께 올 수도 있습니다. 상태 코드보다는 이 사유를 보는 게 더 정확합니다.

---

## 3. 토큰을 직접 까보자

이 구조를 알면 디버깅 방법도 명확해집니다.  
**3~4번 단계를 직접 해보고, 받은 JWT의 `access`를 보면 됩니다.**

```bash
export REG=registry.example.internal:5050
export U='사용자이름'
read -rs -p 'token: ' T; echo     # 토큰은 화면/히스토리에 남지 않게

# 1) registry가 알려주는 인증 서버 주소(realm) 확인
REALM=$(curl -sI https://$REG/v2/ | tr -d '\r' | sed -n 's/.*realm="\([^"]*\)".*/\1/p')
echo "realm=$REALM"

# 2) 여러 저장소에 대해 실제로 받는 권한 확인
for repo in team/web-a team/web-b; do
  printf '%-14s ' $repo
  curl -s -u "$U:$T" "$REALM?service=container_registry&scope=repository:$repo:pull,push" \
  | python3 -c "import sys,json,base64;t=json.load(sys.stdin)['token'].split('.')[1];print(json.loads(base64.urlsafe_b64decode(t+'==')).get('access'))"
done
```

사내 CA로 서명된 인증서를 쓴다면 `curl --cacert <CA 파일>`을 붙여주세요.  
`-k`(인증서 검증 끄기)는 토큰을 실어 보내는 요청이라 웬만하면 쓰지 않는 게 좋습니다.  
registry가 아직 HTTP로만 열려 있다면 `https://`를 `http://`로 바꿔야 하는데,  
그 경우 realm도 HTTP라면 토큰이 평문으로 오가니 확인용으로만 쓰는 게 좋겠습니다.

JWT는 `header.payload.signature` 구조라, 가운데 payload만 base64 디코딩하면 내용을 볼 수 있습니다.

실제로 나왔던 결과는 이랬습니다.

```
team/web-a     [{'type': 'repository', 'name': 'team/web-a', 'actions': ['pull']}]
team/web-b     []
```

**web-b에 대한 권한이 비어 있었습니다.**  
pull용으로 새로 만든 토큰이 그룹 토큰이 아니라, **web-a 프로젝트의 Project Access Token**이었던 겁니다. 😅

결과를 읽는 법을 정리하면 이렇습니다.

| 출력 | 의미 |
|---|---|
| `[{... 'actions': ['pull', 'push']}]` | 토큰 정상 |
| `[]` | 그 저장소에 대한 권한이 없음 → 토큰 종류/역할/scope, 사용자 이름 확인 |
| JSON이 아니거나 401 | 사용자/토큰 조합 자체가 거부됨 |

이 방법의 좋은 점은 **Kubernetes를 전혀 거치지 않고** 토큰만 검증할 수 있다는 겁니다.  
Secret 문제인지, 토큰 문제인지를 깔끔하게 분리할 수 있어요.

노드에서 직접 pull해보는 것도 같은 맥락의 확인 방법입니다.

```bash
# k3s 기준
sudo k3s crictl pull --creds "$U:$T" $REG/team/web-b:develop-1
```

여기서 성공하면 적어도 **이 노드에서, 이 토큰으로는** 받을 수 있다는 뜻입니다.  
그다음은 Pod가 참조하는 Secret의 이름과 내용, 그리고 Pod가 실제로 뜬 노드의 설정을 보면 됩니다.

## 4. 놓치기 쉬운 것: Secret은 namespace 단위

또 하나 헷갈렸던 건, **push용 Secret과 pull용 Secret이 별개**라는 점이었습니다.

| 용도 | 누가 쓰나 | 위치 |
|---|---|---|
| 이미지 **push** | Jenkins의 Kaniko Pod | `jenkins` namespace의 `regcred` |
| 이미지 **pull** | 앱 Pod (`imagePullSecrets`) | **앱이 있는 namespace**의 `regcred` |

Kubernetes Secret은 같은 namespace 안에서만 보입니다.  
이름이 둘 다 `regcred`라서 같은 것처럼 느껴지지만, 실제로는 namespace마다 따로 있는 **다른 Secret**입니다.

그래서 처음에 `jenkins` namespace의 Secret만 바꾸고 나니,

- Jenkins는 새 이미지 push 성공 ✅
- 앱 Pod는 예전 토큰으로 pull하다 실패 ❌

이런 상황이 됐던 거죠.  
앱이 배포되는 namespace(`service`, `service-develop` 등)마다 각각 갱신해줘야 했습니다.

### Secret을 갱신할 때는 create가 아니라 apply로

이미 있는 Secret을 `kubectl create`로 만들려고 하면 `already exists`가 나고 **아무것도 바뀌지 않습니다.**  
에러를 못 보고 넘어가면 "바꿨는데 그대로네?"가 되기 딱 좋습니다.

```bash
kubectl -n service create secret docker-registry regcred \
  --docker-server=registry.example.internal:5050 \
  --docker-username="$U" \
  --docker-password="$T" \
  --dry-run=client -o yaml | kubectl apply -f -
```

`--dry-run=client -o yaml`로 Secret YAML만 만들고, `kubectl apply`로 넘기면  
없으면 만들고, 있으면 바뀐 내용을 기존 Secret에 적용합니다. 지우고 다시 만드는 사이에 Secret이 비는 순간도 없고요.

참고로 `docker-registry`라는 이름 때문에 Docker를 설치해야 하나 싶었는데,  
이건 그냥 **Secret 타입(`kubernetes.io/dockerconfigjson`)** 이름입니다.  
안에는 컨테이너 도구들이 공통으로 쓰는 `config.json` 형식이 들어갈 뿐입니다.

- Kaniko는 이 Secret을 파일로 마운트해서 `config.json`으로 읽고,
- 앱 Pod의 경우엔 **kubelet**이 Secret에서 인증 정보를 꺼내 containerd 같은 런타임에 넘겨줍니다.

Docker 데몬은 어디에도 필요 없습니다.

## 5. 어떤 토큰을 써야 할까?

이번에 GitLab 토큰 종류도 한 번 정리했습니다.

| | Personal Access Token | Group Access Token | Group Deploy Token |
|---|---|---|---|
| 접근 범위 | 그 사용자가 접근 가능한 모든 프로젝트 | 그룹 아래 프로젝트 (역할 기준) | 그룹 아래 프로젝트 |
| 권한 | 사용자 권한 그대로 | 지정한 역할(role)과 scope | Git 저장소 읽기, registry 읽기·쓰기 (scope별) |
| 사람 계정과 무관 | ❌ | ✅ (봇 사용자) | ✅ |
| 만료 | 버전에 따라 필수 | **필수** | 선택 |
| API 호출 | ✅ | ✅ (`api` scope 추가 시) | ❌ |

이번에 처음 쓴 토큰이 문제였던 이유도 표에서 보입니다.

- **Project Access Token**: 그 프로젝트에만 권한이 있다 → 새 프로젝트 이미지는 못 받는다
- **관리자 PAT**: 어디든 접근되지만, 권한이 너무 크고 사람 계정에 묶여 있다

(표는 일반적인 비공개 프로젝트 기준입니다. 실제 범위는 역할, scope, 프로젝트 공개 범위 설정에 따라 달라질 수 있어요.)

결국 이번에는 **Group Access Token**으로 통일했습니다.

- Role: **Developer** (push까지 필요하므로. pull 전용이라면 Reporter 이상)
- Scope: `read_registry`, `write_registry`

그룹 아래 프로젝트라면 새로 생겨도 다시 만들 필요가 없습니다.  
registry 용도로만 쓴다면 만료 없이 둘 수 있는 **Group Deploy Token**도 좋은 선택입니다.

한 가지 팁으로, Group/Project Access Token을 만들면 GitLab이 **봇 사용자**를 그룹 멤버로 추가합니다.  
registry 로그인 사용자 이름에는 토큰 이름보다 이 **봇 사용자 이름**(그룹 → Members에서 확인)을 넣는 게 확실합니다.

## 6. 덤: 터미널에 토큰을 붙여넣을 때

디버깅하면서 한 번 더 삽질한 게 있어서 덧붙입니다.

```bash
read -rs -p 'token: ' T; echo
```

이 줄을 **여러 줄 명령과 함께 한꺼번에 붙여넣으면**,  
`read`가 사용자 입력 대신 붙여넣은 내용의 다음 줄이나 빈 줄을 입력으로 먹어버릴 수 있습니다.  
제 경우엔 토큰이 빈 값인 채로 다음 명령이 실행됐어요.

`read`는 따로 한 줄만 실행하고 직접 입력하는 게 안전합니다.  
`echo ${#T}`로 길이가 0이 아닌지 확인해보는 것도 좋고요.

## 마무리

정리하면,

- `insufficient_scope`는 **요청에 필요한 권한이 토큰에 없다**는 뜻이다
- GitLab `/jwt/auth`에서 토큰을 받아 **`access`를 디코딩**하면 실제 권한을 바로 확인할 수 있다
- push용(Jenkins)과 pull용(앱 namespace) Secret은 **별개**이고, namespace마다 갱신해야 한다
- Secret 갱신은 `create --dry-run=client -o yaml | apply`로
- 저장소가 여러 개라면 **그룹 단위 토큰**이 관리하기 편하다

에러 메시지만 보면 "repository does not exist or may require authorization"처럼 애매하게 나오지만,  
토큰 한 번 까보면 꽤 명확하게 원인이 보이더라구요.  
같은 에러로 고생하시는 분께 도움이 되길 바랍니다.

감사합니다. 😊
