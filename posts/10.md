## 들어가며
안녕하세요.  
AWS를 처음 만질 때는 보통 서비스부터 보게 됩니다.

- EC2는 어떻게 띄우는지
- S3 권한은 어디서 막는지
- VPC는 왜 이렇게 복잡한지
- CloudWatch 로그는 어디서 보는지

저도 처음에는 이런 것들이 먼저 궁금했습니다.  
일단 화면에 뭔가 떠야 하고, 외부에서 접속이 되어야 하고,  
에러가 나면 로그라도 봐야 하니까요.

그런데 리소스가 조금씩 늘어나면 질문이 살짝 바뀝니다.  
저도 단일 계정에서 이것저것 만들다 보니, 어느 순간부터 서비스 자체보다  
"이걸 어디에 두고 어떻게 구분해야 하지?" 쪽이 더 신경 쓰였습니다.

예를 들어 실습용으로 만든 EC2와, 실제로 오래 켜둘 리소스가 같은 계정에 있고  
테스트하다 만든 IAM Role도 그대로 남아 있고,  
CloudWatch 로그를 봐도 이게 어떤 실습에서 나온 건지 바로 안 보이는 상황이 생깁니다.

비용도 비슷했습니다.  
분명 작은 테스트였던 것 같은데 비용이 조금씩 쌓이고,  
막상 Cost Explorer를 보면 어떤 리소스가 어떤 목적이었는지 다시 되짚어봐야 했습니다.

이쯤 되면 AWS 콘솔을 열 때마다 약간 찝찝해집니다.

> 이걸 같은 AWS 계정에 계속 둬도 되나?  
> 개발용 리소스랑 운영용 리소스가 섞이면 나중에 괜찮을까?  
> 사람이 늘어나면 권한은 어떻게 줘야 하지?  
> 문제가 생겼을 때 어디까지 영향을 받을까?

처음에는 IAM User만 잘 만들면 되는 줄 알았습니다.  
하지만 조금 보다 보니 계정 관리는 단순히 사용자 하나 만드는 문제가 아니더군요.

돌아보면 AWS 계정 관리는 거창한 아키텍처 이야기라기보다,  
계속 같은 질문으로 돌아오는 일에 가까웠습니다.

- 리소스를 어디에 둘 것인가
- 사람에게 어떤 계정 접근을 줄 것인가
- 계정마다 어디까지 허용할 것인가
- 문제가 생겼을 때 로그를 어디에 남길 것인가
- 이 구조를 어떻게 반복 가능하게 만들 것인가

이번 글은 그 흐름대로 정리해보려 합니다.  
정답에 가까운 설계라기보다는, 제가 단일 계정으로 쓰다가 어떤 지점에서 불편했고  
왜 Organizations나 IAM Identity Center 같은 키워드를 보게 됐는지에 가깝습니다.

## 1. 단일 계정의 편의와 불편

처음부터 계정을 여러 개 만들 필요는 없다고 생각합니다.  
개인 실습이나 작은 프로젝트라면 계정 하나가 훨씬 편합니다.

- 결제도 한 곳에서 보면 되고
- IAM도 복잡하지 않고
- 리소스 찾기도 쉽고
- 실습할 때 생각할 것도 적습니다

EC2 한 대 띄우고, S3 버킷 하나 만들고,  
RDS 하나 붙여보는 정도라면 굳이 구조를 크게 가져갈 이유가 없습니다.

문제는 그 다음입니다.  
한 계정으로 계속 만들다 보면, 처음에는 편했던 단순함이 나중에는 오히려 애매해집니다.

처음에는 단순했던 계정 안에 어느 순간부터 이것저것 붙기 시작합니다.

- 개발용 EC2
- 운영 비슷하게 쓰는 RDS
- 테스트용 S3 버킷
- Lambda, CloudFront, Route 53
- 임시로 만든 IAM Role
- 지우기 애매한 CloudWatch Log Group

이쯤 되면 콘솔에서 리소스를 보는 것부터 조금씩 복잡해집니다.  
저는 특히 이런 것들이 계속 걸렸습니다.

- 테스트용으로 만든 IAM 권한이 생각보다 넓게 남아 있음
- 비용을 볼 때 어떤 게 실습이고 어떤 게 계속 켜둘 리소스인지 다시 확인해야 함
- 이름을 대충 지은 리소스가 쌓이면 나중에 지워도 되는지 애매함
- CloudTrail이나 CloudWatch 로그를 봐도 어떤 맥락의 이벤트인지 바로 안 보임
- 실수로 지웠을 때 영향 범위가 어디까지인지 머릿속에서 한 번 더 계산해야 함

하나씩 보면 별일 아닌 것 같지만,  
이게 쌓이면 "계정 하나로 계속 가도 되나?" 라는 생각이 들 수밖에 없습니다.

그래서 제 기준에서는 계정 관리가 **계정을 나눠야 하나?** 라는 질문에서 시작됐습니다.

## 2. 계정이라는 경계

AWS 계정을 처음에는 큰 폴더처럼 생각하기 쉽습니다.  
저도 처음엔 리소스를 담는 박스 정도로 봤습니다.

그런데 단일 계정에서 불편함이 생기고 나니, 조금 다르게 보이기 시작했습니다.

> 계정은 리소스를 담는 공간이기도 하지만,  
> 동시에 권한과 사고 범위를 나누는 경계에 더 가깝다.

계정을 나누면 생각보다 많은 것이 같이 나뉩니다.

- IAM 권한 범위
- 리소스 소유 범위
- 비용 집계 단위
- CloudTrail 이벤트
- 서비스 할당량
- 실수했을 때의 영향 범위

예를 들어 `dev` 계정에서 누군가 VPC를 잘못 지웠다고 해도,  
`prod` 계정의 VPC까지 같이 날아가지는 않습니다.

말로만 보면 너무 당연한 이야기인데, 막상 리소스가 섞이기 시작하면 이 차이가 꽤 크게 느껴집니다.  
계정을 나눈다는 건 단순히 정리정돈을 하는 게 아니라,  
실수나 장애가 번질 수 있는 범위를 미리 잘라두는 것에 가깝습니다.

![AWS 계정별 보안 경계 예시](/10/2.png)
*한 계정에서 문제가 생겨도 다른 계정까지 같이 무너지지 않게 경계를 나누는 것이 목적입니다.*

그러면 다음 질문이 생깁니다.

> 계정을 나누는 건 알겠는데, 여러 계정을 어떻게 한 곳에서 관리하지?

이쯤부터 AWS Organizations를 찾아보기 시작했습니다.

## 3. Organizations와 계정 구조

계정을 나누는 것까지는 이해가 됐는데, 바로 다음 문제가 생깁니다.

> 그럼 여러 계정을 각각 따로 로그인해서 관리해야 하나?

여기서 AWS Organizations를 보게 됐습니다.

처음 보면 기능이 꽤 많아 보입니다.  
문서도 많고, 관련 용어도 한 번에 튀어나와서 살짝 부담스럽더군요.

그래도 처음에는 네 가지만 잡아도 흐름은 보였습니다.

| 개념 | 설명 |
|:---|:---|
| Management Account | 조직을 만들고 전체 계정을 관리하는 계정 |
| Member Account | 조직에 속한 개별 AWS 계정 |
| OU | 계정을 그룹으로 묶는 단위 |
| SCP | 계정이나 OU에 적용하는 상위 권한 제한 |

Organizations를 쓰면 여러 계정을 하나의 결제 단위로 묶을 수 있고,  
계정들을 OU 단위로 정리할 수도 있더군요.

아... 그러니까 계정을 여러 개 만든다고 해서  
그 계정들이 전부 따로 노는 건 아니구나 싶었습니다.

가장 먼저 떠올릴 수 있는 건 환경 기준입니다.

```txt
management
dev
staging
prod
```

제가 이해하기로는, 이 정도만 나눠도 단일 계정보다는 기준이 꽤 선명해집니다.  
적어도 "이 리소스가 어디에 있어야 하지?"라는 질문에 답하기가 조금 쉬워집니다.

- `management`: 조직과 결제 관리
- `dev`: 개발과 실험
- `staging`: 운영 전 검증
- `prod`: 실제 서비스 운영

여기서 더 운영에 가까운 구조를 고민한다면,  
보안이나 공통 인프라용 계정을 따로 두는 방향도 같이 보게 됩니다.

```txt
Root
├─ Security
│  ├─ security
│  └─ log-archive
├─ Infrastructure
│  └─ shared-services
└─ Workloads
   ├─ dev
   ├─ staging
   └─ prod
```

![AWS Organizations OU와 정책 경계 예시](/10/3.png)
*OU는 계정을 묶는 기준이고, SCP는 그 묶음 위에서 할 수 없는 일을 정해두는 장치로 보면 이해하기 쉽습니다.*

자료를 보면서 제가 메모한 각 계정의 역할은 대략 이렇습니다.  
실무에서 그대로 가져다 쓰자는 의미보다는,  
"왜 굳이 이렇게까지 나누지?"를 보기 위한 예시에 가깝습니다.

| 계정 | 역할 |
|:---|:---|
| management | 조직 관리, 결제, 계정 생성 |
| security | 보안 서비스와 감사 설정 관리 |
| log-archive | CloudTrail, Config, VPC Flow Logs 등 중앙 로그 보관 |
| shared-services | 공통 네트워크, CI/CD, DNS, 공통 도구 운영 |
| dev | 개발 및 실험 환경 |
| staging | 운영 전 검증 환경 |
| prod | 실제 서비스 운영 환경 |

물론 개인 실습에서 이 구조를 전부 만들 필요는 없습니다.  
오히려 처음부터 너무 크게 만들면 계정 관리 자체가 부담이 될 수 있습니다.

그래도 이런 구조가 왜 나오는지는 알아두면 좋겠더군요.  
중요한 리소스일수록 더 강한 경계 안에 두고,  
로그나 보안처럼 공통으로 봐야 하는 것은 따로 모으는 방식입니다.

다만 여기까지 보고 나니, Organizations는 계정을 묶어주는 쪽에 더 가깝게 느껴졌습니다.  
계정을 묶었다면, 그 다음에는 **누가 어떤 계정에 들어갈 수 있는지** 를 고민하게 됩니다.

## 4. IAM과 Identity Center 접근 관리

계정을 나눴다고 해서 권한 문제가 자동으로 해결되지는 않았습니다.  
오히려 계정이 늘어나면 "누가 어디에 들어갈 수 있지?"를 더 자주 보게 됩니다.

저는 여기서 IAM과 IAM Identity Center를 억지로 한 덩어리로 보지 않는 게 이해하기 좋았습니다.

| 구분 | 역할 |
|:---|:---|
| IAM | 한 계정 안에서 사용자, 역할, 정책을 관리 |
| IAM Identity Center | 여러 계정에 사람이 접근하는 방식을 중앙에서 관리 |

IAM은 한 계정 안에서 권한을 만질 때 가장 먼저 보게 되는 영역입니다.  
단일 계정에서는 여기까지만 봐도 대부분의 실습은 진행할 수 있었습니다.

- IAM User
- IAM Group
- IAM Role
- IAM Policy

결국 **이 계정 안에서 누가 무엇을 할 수 있는가**를 다루는 쪽이라고 보면 이해가 쉬웠습니다.

작은 실습에서는 IAM만으로도 충분할 수 있습니다.  
하지만 계정이 여러 개로 늘어나면 IAM만으로는 관리가 꽤 피곤해 보였습니다.

예를 들어 한 사람이 `dev`, `staging`, `prod` 계정에 각각 접근해야 한다고 가정해보면,  
각 계정마다 IAM User를 따로 만들고 권한을 맞추는 방식은 금방 귀찮아집니다.

이때 IAM Identity Center를 같이 보면, 사용자와 그룹을 중앙에서 관리하고  
각 계정에 어떤 권한 세트를 줄지 연결하는 식으로 접근할 수 있습니다.

예를 들면 이런 식으로 나눠볼 수 있습니다.

- 개발자는 `dev` 계정에 PowerUser 권한
- 운영자는 `prod` 계정에 제한된 Admin 권한
- 보안 담당자는 모든 계정에 ReadOnly 권한
- 외부 협력자는 특정 계정에만 제한 접근

사람이 입사하거나 퇴사할 때도 계정마다 IAM User를 뒤지는 방식보다는  
중앙에서 접근을 관리하는 쪽이 더 자연스러운 방향으로 보였습니다.

그래서 머릿속에서는 일단 이렇게 나눠두는 게 편했습니다.

| 구분 | 역할 |
|:---|:---|
| Organizations | 계정 자체를 묶고 관리 |
| IAM Identity Center | 사람이 계정에 접근하는 방식을 관리 |
| IAM Role/Policy | 실제 계정 안에서 동작하는 권한 정의 |

그런데 여기서 끝이 아닙니다.  
사람에게 권한을 주는 것과 별개로,  
계정 자체가 넘지 말아야 할 선도 생각해볼 필요가 있습니다.

이때 다시 SCP가 나옵니다.

## 5. SCP와 권한 상한선

Organizations를 보다 보면 SCP가 자주 나옵니다.  
처음에는 IAM Policy랑 뭐가 다른지 조금 헷갈렸습니다.

IAM Policy는 계정 안에서  
**누가 무엇을 할 수 있는지** 를 다룹니다.

SCP는 조직이나 OU 차원에서  
**이 계정이 어디까지 할 수 있는지** 상한선을 잡는 쪽에 가깝습니다.

조금 다르게 표현하면, SCP는 권한을 주는 쪽이 아니었습니다.  
"이건 아무리 권한이 있어도 하지 못한다"를 정해두는 장치에 가깝다고 봤습니다.

이 차이를 이해하고 나니 IAM과 SCP를 같은 선상에서 보면 헷갈리는 이유가 보였습니다.

예를 들면 아래처럼 서울 리전이 아닌 곳에서 EC2 생성을 막는 식으로 생각해볼 수 있습니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Deny",
      "Action": "ec2:RunInstances",
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:RequestedRegion": "ap-northeast-2"
        }
      }
    }
  ]
}
```

이렇게 해두면 계정 안의 사용자가 `AdministratorAccess`를 가지고 있어도,  
서울 리전이 아닌 곳에서는 EC2를 만들 수 없습니다.

운영에 가까운 환경을 가정한다면, 이런 제한이 꽤 도움이 될 수 있습니다.  
특히 실수로 리전을 잘못 고르거나, 지우면 안 되는 로그를 건드리는 상황을 막는 데 의미가 있어 보였습니다.

- 특정 리전 사용 금지
- 루트 사용자 작업 제한
- CloudTrail 삭제 금지
- S3 Public Access 차단
- 고비용 리소스 생성 제한

물론 SCP를 너무 강하게 걸면 정상적인 작업도 막힐 수 있습니다.  
그래서 처음부터 복잡하게 만들기보다는,  
"정말 하면 안 되는 것"부터 막아보는 쪽이 낫다고 봅니다.

여기까지 보면 계정을 나누고, 접근 권한을 나누고,  
계정별 상한선까지 잡는 흐름이 어느 정도 잡힙니다.  
단일 계정에서는 한 덩어리로 보이던 것들이 조금씩 분리되는 느낌이었습니다.

그 다음으로 자연스럽게 보게 되는 것은 로그입니다.  
문제가 생겼을 때 확인할 근거가 남아 있어야 하니까요.

---

## 6. 로그 계정과 감사 근거

CloudTrail이나 CloudWatch Logs는 각 계정에 그냥 둬도 동작합니다.  
처음에는 굳이 로그 계정을 따로 둬야 하나 싶을 수 있습니다.

그런데 보안 관점에서는 이야기가 조금 달라집니다.

운영 계정에 문제가 생겼다고 가정해보겠습니다.  
만약 공격자나 실수한 사용자가 운영 계정 안에서 높은 권한을 얻었다면,  
그 계정 안에 있는 로그도 같이 지우거나 바꾸려 할 수 있습니다.

그래서 다중 계정 자료에서는 중요한 로그를 `log-archive` 같은 별도 계정으로 모으는 구조가 자주 나옵니다.  
처음에는 조금 과한가 싶었는데, "문제가 생긴 계정 안에 로그도 같이 있다"라고 생각하면 이유가 보였습니다.

- CloudTrail 조직 trail
- AWS Config 기록
- VPC Flow Logs
- ALB Access Logs
- GuardDuty Findings

![다중 계정 환경의 중앙 로그 아카이브 예시](/10/4.png)
*워크로드 계정에서 발생한 로그를 별도 계정으로 모아두면, 문제가 생긴 뒤에도 확인할 근거를 남기기 좋습니다.*

이렇게 해두면 워크로드 계정에서 문제가 생기더라도,  
감사 기록을 조금 더 안전하게 보관하는 방향으로 설계할 수 있습니다.

결국 로그 계정을 나누는 이유는 단순히 로그를 예쁘게 모으기 위해서가 아니었습니다.  
문제가 생겼을 때 **무슨 일이 있었는지 확인할 수 있는 마지막 근거**를 남기기 위해서입니다.

여기까지 보고 나니, Control Tower가 왜 같이 언급되는지도 조금 이해가 됐습니다.  
계정을 잘 나누는 것보다, 그 구조를 계속 같은 방식으로 만드는 일이 더 어려울 수 있겠더군요.

## 7. Control Tower와 자동화

다중 계정 자료를 찾다 보면 Control Tower도 거의 같이 나옵니다.  
처음에는 "이건 또 뭐지..." 싶었습니다.

계정 생성, 기본 보안 설정, 로그 보관, 가드레일 적용 같은 것들을  
매번 손으로 맞춘다고 생각하면 꽤 번거로울 것 같았습니다.

Control Tower는 이런 기본 구성을 어느 정도 표준화해서 만들어주는 쪽으로 이해했습니다.  
지금 단계에서 바로 써야 하는 도구라기보다는, Organizations를 어느 정도 만져본 뒤에 봐도 늦지 않겠다는 생각이 들었습니다.

처음부터 Control Tower로 들어가면 조금 무겁게 느껴질 수 있습니다.  
특히 아직 Organizations, OU, SCP가 익숙하지 않다면  
Control Tower가 뭘 대신 해주는지도 잘 안 보일 수 있습니다.

저라면 순서를 이렇게 잡을 것 같습니다.

1. 단일 계정에서 IAM, VPC, CloudTrail을 먼저 이해한다
2. Organizations로 계정을 묶어본다
3. OU를 만들고 계정을 배치해본다
4. IAM Identity Center로 계정 접근을 연결해본다
5. 간단한 SCP를 걸어본다
6. 로그 계정을 분리해본다
7. 그 다음 Control Tower가 무엇을 자동화해주는지 본다

Control Tower를 먼저 외우기보다는,  
Organizations에서 계정과 정책이 어떻게 움직이는지 한 번 직접 보는 편이 낫다고 생각합니다.

그래야 Control Tower가 편한 도구인지,  
아니면 지금 단계에서는 과한 도구인지도 판단할 수 있습니다.

---

## 8. 작은 실습 흐름

처음부터 회사 수준의 랜딩존을 만들 필요는 없습니다.  
작게 해본다면 세 계정 정도면 충분해 보입니다.

```txt
management
dev
prod
```

제가 작게 실습한다면 이렇게 잡아볼 것 같습니다.

1. Management Account에서 Organizations 활성화
2. `dev`, `prod` 멤버 계정 생성
3. `Workloads` OU 생성 후 두 계정 배치
4. IAM Identity Center에서 사용자와 권한 세트 연결
5. `prod` 계정에 간단한 SCP 적용
6. CloudTrail 조직 trail 활성화

확인할 것은 많지 않습니다.

- `dev`에서는 실험 리소스를 만들 수 있는지
- `prod`에서는 제한한 작업이 실제로 막히는지
- CloudTrail 이벤트가 남는지
- 계정별 비용이 분리되어 보이는지
- 사용자에게 계정별로 다른 권한을 줄 수 있는지
- 계정을 나눈 이유를 스스로 설명할 수 있는지

여기까지 해보면 "계정이 여러 개 있다" 수준은 넘어갈 수 있습니다.  
왜 나눴는지, 무엇을 막고 싶은지, 누가 접근할 수 있는지,  
어떤 로그를 남길지까지 같이 보게 되니까요.

---

## 마치며

AWS 계정 관리는 처음부터 꼭 무겁게 가져갈 필요는 없다고 생각합니다.

작은 실습이나 개인 프로젝트라면 계정 하나로도 충분합니다.  
오히려 처음부터 계정을 나누느라 시간을 너무 쓰면,  
정작 서비스 자체를 이해하는 속도가 느려질 수도 있습니다.

결국 리소스가 늘어나고, 운영 환경을 따로 봐야 하고,  
권한과 비용과 로그가 섞이기 시작하면 어느 순간 계정을 나누는 기준이 필요해집니다.

저는 이 주제를 보면서 결국 아래 질문으로 돌아오게 되었습니다.

> 이 리소스는 어느 계정에 있어야 하지?  
> 이 계정에는 누가 접근할 수 있어야 하지?  
> 이 계정에서는 무엇을 절대 못 하게 해야 하지?  
> 문제가 생기면 어디까지 영향을 받을까?  
> 나중에 원인을 추적할 로그는 남아 있을까?

이 질문에 답하려고 하다 보면,  
계정 분리는 단순한 관리 편의가 아니라 운영 방식의 일부라는 생각이 듭니다.

아직 저도 다중 계정 구조를 모든 상황에 맞게 설계할 수 있다고 보지는 않습니다.  
그래도 단일 계정에서만 AWS를 볼 때와, 계정 자체를 경계로 보고 AWS를 볼 때는  
확실히 고민의 범위가 달라지는 것 같습니다.
